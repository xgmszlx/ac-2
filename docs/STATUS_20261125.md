### 根因（两段，第一段是真凶）

**① `move_base` 启动即 FATAL 退出 —— teb 插件根本没注册**

```
[FATAL] [...] Failed to create the teb_local_planner/TebLocalPlannerROS planner, are you sure it is
properly registered and that the containing library is built? Exception: According to the loaded plugin
descriptions the class teb_local_planner/TebLocalPlannerROS with base class type nav_core::BaseLocalPlanner
does not exist. Declared types are  base_local_planner/TrajectoryPlannerROS dwa_local_planner/DWAPlannerROS
```
→ `logs/p1diag_sim.log:238`。

机制：`env.sh` 把 `localroot/opt/ros/noetic/share` 加进了 `ROS_PACKAGE_PATH`，但
`run_task.sh` 随后 `source ws/devel/setup.bash`，catkin 的 setup.bash **整体覆盖**
`ROS_PACKAGE_PATH`（变成 `<ws>/src:/opt/ros/noetic/share`），localroot 前缀被抹掉。实测：

```
$ rospack find teb_local_planner      -> [rospack] Error: package 'teb_local_planner' not found
$ rospack plugins --attrib=plugin nav_core -> 只有 dwa/base_local_planner/navfn/…（没有 teb）
```
（deb 文件确实在 `localroot/opt/ros/noetic/{share,lib}` 里，只是不可见。）

**② 由此产生的链式症状（前几轮一直以为是 Filter.py 自己的 bug）**

move_base 死了 → 没有 global costmap publisher、没有 `/robot_1/move_base_node/NavfnROS/make_plan` 服务 →
`Filter.py` 在 `SimpleRobot.Robot.__init__` 的 `rospy.wait_for_service(...)` 上**永久阻塞**，
连 "Filter is waiting for the map." 都打不出来 → `filtered_points` 从来没有 publisher →
决策器永远没有候选 → 从不下发 goal。**Filter.py 的 6 个过滤条件一次都没被执行过**，
所以之前"调 information_threshold / 关 costmap 清障阈值"的思路是打偏的。

### 修复

`run_task.sh`：在 `source ws/devel/setup.bash` 之后把 localroot 前缀重新前置，并加一条

但随后暴露两个新问题（都有 traceback）：

**② `always_send_full_costmap: false` → 重生后的 Filter 永远等不到全局 costmap**

`ws/src/explorb_scenarios/param/global_costmap_params.yaml` 沿用作者值 `false`：costmap_2d 只在
启动时发一次完整栅格，之后只发 `costmap_updates` 增量。Filter 用 `gridValue()` 查任意格，
必须拿到完整栅格；节点一次 respawn 之后就再也收不到 → 卡在
`Filter is waiting for the global costmap.`（`logs/p1loop_agent.log` 第 1427–1434 行）。
**已改 `true`**（注释写清理由）。

**③ Filter 自身两处会中断整条链的异常**

| 异常 | 位置 | 处理 |
|---|---|---|
| `tf2.TransformException: Could not find a connection between 'map' and 'base_link'` | `Filter.py` 的 `waitForTransform`（`~robot_frame` 未从 launch 传入，用了默认 `base_link`） | `frontiers.launch` 把 `robot_frame` 传给 Filter（`base_footprint`）；`waitForTransform` 改为非致命 |
| `rospy.service.ServiceException: unable to connect to service: [Errno 111] Connection refused`（`make_plan`） | `Filter.py` 调 `robot.makePlan()` | try/except + `logwarn_throttle`，**查不到可达性时保留该 frontier**（不是删除） |
| `Robot.__init__` 里 `waitForTransform` 抛异常 | `SimpleRobot.py:39`（作者代码，Filter/Controller 共用） | 改为非致命，交给下面的重试循环 |

**④ 还发现一个纯 Python 侧的隐藏 bug（离线复现，未在仿真里触发到，但必然触发）**

`informationGain_NUMBA` 用显式 numba 签名 `nb.int64[:]`，而 rospy 把 `int8[]` 反序列化成
`array.array('b')`，`np.array(...)` 得到的是 **int8** 数组：

```
[PASS] int8 dispatch is rejected (documents the old bug)  np.array(array("b",...)).dtype=int8
TypeError: No matching definition for argument type(s) ... array(int8, 1d, C)
```
→ 已在 `Filter.mapCallBack` 里**每条地图消息转一次 int64**（`map_arr_`），不再每个质心转一次；
同时保留 try/except 回退到纯 Python 实现。证据：`tools/selfcheck_loo.py` 第 1 项。
